# 클로드 문서 — 사용 안내

## 1. 이게 무엇인가

이 폴더(`CLAUDE.md`, `.claude/agents/`, `docs/`)를 프로젝트에 복사하면, Claude Code가 혼자 일하는 비서처럼 움직이지 않고 역할이 나뉜 팀처럼 일합니다. 사람 회사에 기획자와 실무자가 따로 있듯, Claude 안에서도 판단하는 역할과 손을 움직이는 역할이 나뉩니다.

팀에는 일곱 역할이 있습니다. 지휘자는 계획을 세우고 결과를 검증합니다. 실행자는 실제로 코드를 만듭니다. 보조는 탐색이나 반복 같은 단순한 일을 합니다. 검증자는 실행자의 결과물을 고치지 않고 검사만 합니다. 소통자는 사용자가 대화하는 유일한 창구입니다. 요청자는 사용자가 직접 해야 하는 일을 안내서로 만듭니다. 검사자는 완성된 화면이나 기능을 실제로 눌러보고 검사합니다.

역할마다 쓰는 모델과 생각하는 깊이(effort, 9번 용어 사전 참고)가 다릅니다. 쉬운 일에는 저렴한 모델을, 어려운 판단에는 성능 좋은 모델을 씁니다. 이렇게 나누는 이유는 크게 두 가지입니다. 하나는 비용입니다 — 모든 일을 가장 비싼 모델에 맡기지 않아도 됩니다(8번 참고). 다른 하나는 품질입니다 — 검증자처럼 구현 과정을 모르는 눈이 결과를 다시 보면 놓친 문제를 더 잘 찾습니다.

이 팀의 구성은 2번에서, 처음 켜는 방법은 3번에서 이어집니다.

## 2. 폴더에 든 것

- `CLAUDE.md` — 팀의 작업 규칙을 적은 문서입니다. Claude Code가 프로젝트를 열면 자동으로 읽습니다. 사용자가 손댈 필요는 없습니다.
- `.claude/agents/` — 역할 카드 9개(`executor.md`, `executor-max.md`, `executor-sonnet.md`, `verifier.md`, `helper.md`, `runner.md`, `communicator.md`, `requester.md`, `qa.md`)입니다. 각 카드에는 그 역할이 쓸 모델·effort·지켜야 할 규칙이 적혀 있습니다.
  - 파일 이름은 역할과 그대로 대응합니다: executor=실행자(max·sonnet은 어려운 일·쉬운 일용 변형), verifier=검증자, helper=보조, runner=실행기(기계 작업), communicator=소통자, requester=요청자, qa=검사자.
- `ADOPTION.md` — 이미 진행 중인 프로젝트에 이 체계를 얹을 때 지휘자가 따르는 절차입니다(3-1 참고). 새 프로젝트에는 필요 없습니다.
- `docs/` — 프로젝트가 진행되며 채워지는 기록 템플릿입니다. 새 프로젝트라면 비어 있는 것이 정상이고, Claude가 첫 작업을 시작하며 채워 나갑니다. 안에는 성격이 다른 다섯 묶음이 있습니다.
  - `docs/00~04_*.md` — 프로젝트의 목표·구조·위험·결정을 적는 상태 문서입니다.
  - `docs/briefs/` — 브리프(B-###)·설명과 브리핑(G-###)·워크시트(W-###)가 쌓이는 곳입니다.
  - `docs/specs/` — 기능 설명서(F-###)가 쌓이는 곳입니다.
  - `docs/tasks/` — 일감 카드(T-###)와 전체 현황판(`BACKLOG.md`)이 있는 곳입니다.
  - `docs/experience/` — 일하며 얻은 경험(에이전트 배정 기록, 오류 사례, 노하우)이 쌓이는 곳입니다.

## 3. 처음 설정 5단계

한 번만 하면 되는 준비입니다. 번호 순서대로 진행합니다.

1. 프로젝트 폴더에 `CLAUDE.md`, `.claude/agents/`, `docs/`를 복사합니다.
2. Claude Code에서 그 폴더를 엽니다.
3. 지휘자 세션(세션 = 채팅창 하나)을 만듭니다. 모델을 Claude Fable 5.1로 고르고, 세션에서 `/effort max`를 입력합니다. 세션 제목은 "지휘자"로 둡니다.
4. 소통자 세션을 만듭니다. 모델은 Claude Sonnet 5, `/effort medium`을 입력합니다. 세션 제목은 "소통자"입니다. 첫 메시지로 정확히 다음을 보냅니다.
   > 이 세션은 소통자다. 세션 제목을 '소통자'로 설정하라. .claude/agents/communicator.md를 읽고 그 역할로 일하라. CLAUDE.md의 지휘자 규칙은 적용하지 않는다
5. 요청자 세션을 만듭니다. 모델은 Claude Sonnet 5, `/effort high`를 입력합니다. 세션 제목은 "요청자"입니다. 첫 메시지로 정확히 다음을 보냅니다.
   > 이 세션은 요청자다. 세션 제목을 '요청자'로 설정하라. .claude/agents/requester.md를 읽고 그 역할로 일하라. CLAUDE.md의 지휘자 규칙은 적용하지 않는다

여기까지가 기본 3개 창입니다. 이 다음부터는 필요할 때만 창을 추가로 엽니다.

**검사자 세션 (조건부)** — 화면이나 기기를 조작해야 하는 제품(앱, 웹사이트 등)일 때만 엽니다. 화면이 없는 프로젝트(예: 자동화 스크립트)라면 열지 않아도 됩니다. 모델은 Claude Sonnet 5, `/effort high`, 세션 제목은 "검사자"입니다. 첫 메시지로 정확히 다음을 보냅니다.
> 이 세션은 검사자다. 세션 제목을 '검사자'로 설정하라. .claude/agents/qa.md를 읽고 그 역할로 일하라. CLAUDE.md의 지휘자 규칙은 적용하지 않는다

**실행자 세션 (조건부)** — 지휘자가 "이 모듈은 새 세션에서 하자"고 할 때만 엽니다. 이때 요청자가 실행 명령·모델·제목·첫 메시지를 복사 가능한 블록으로 담은 개설 워크시트를 만들어 소통자를 통해 보내 줍니다. 평소에는 지휘자가 눈에 보이지 않는 곳에서 실행자를 자동으로 띄우므로, 사용자가 매번 직접 열 필요는 없습니다. 여는 경우 모델은 Claude Opus 5이고, 세션 제목은 티켓 번호(예: T-003)입니다. 첫 메시지로 정확히 다음을 보냅니다.
> 이 세션은 실행자다. CLAUDE.md의 지휘자 규칙은 적용하지 않는다. 세션 제목을 T-###으로 설정하라. .claude/agents/executor.md를 읽고 docs/tasks/T-###.md를 수행. 소유 파일 밖 수정 금지. 끝나면 티켓의 '보고' 절에 ①~④를 쓰고 커밋한 뒤 '지휘자'에게 알려라

터미널을 쓸 줄 안다면 `claude -w 모듈명 --model opus`로 열어도 됩니다. 그 모듈 전용 작업 폴더(워크트리, 여러 창이 같은 파일을 동시에 건드려도 꼬이지 않도록 나눠 둔 폴더)가 자동으로 생깁니다.

첫 메시지를 반드시 정확히 보내야 하는 이유가 있습니다. 이 선언이 없으면 새 세션도 `CLAUDE.md`를 읽고 지휘자처럼 행동하며, 원치 않는 하위 위임을 시작할 수 있습니다.

## 3-1. 이미 진행 중인 프로젝트에 도입하려면

문서·코드·작업 방식이 이미 있는 프로젝트라면 위 5단계 대신 `ADOPTION.md`(기존 프로젝트 도입 가이드)를 따릅니다. 핵심은 세 가지입니다. 기존 문서는 지우거나 옮기지 않고 `docs/`에 요약과 링크만 얹습니다. 코드의 "누가 어느 폴더를 맡나" 지도를 먼저 만들고, 그 전에는 동시 작업을 시키지 않습니다. 작은 기능 하나로 시험 운행을 한 뒤 확장합니다.

사용자가 할 일은 두 가지뿐입니다. 시작할 때 다섯 가지 질문(기존 CLAUDE.md 유무, 창구 인원, 화면·기기 유무, Codex 사용, 브랜치 정책)에 답하고, 요청자가 만든 워크시트대로 세션을 엽니다. 나머지는 지휘자가 합니다. 지휘자 세션의 첫 요청은 "ADOPTION.md대로 도입해"입니다. `ADOPTION.md`도 프로젝트 폴더에 함께 복사합니다.

## 4. 평소 일하는 방법

사용자는 **소통자 창에서** 말합니다. 다른 창에는 새 요청을 넣지 않습니다. 지휘자는 판단하느라 바쁘므로, 사용자와의 대화는 소통자가 대신 맡아 옮겨 줍니다. 예외는 하나입니다. 지휘자가 직접 묻는 짧은 예/아니오와 선택(5번)은 지휘자 창에서 답합니다. 다른 창이 대신 전달한 승인은 승인으로 치지 않기 때문입니다. 흐름은 다음과 같습니다.

1. 소통자에게 원하는 것을 말합니다.
2. 소통자가 몇 가지를 되묻고, 정리한 내용을 "브리프"(B-###, `docs/briefs/`에 저장되는 요구사항 정리 문서)로 만들어 지휘자에게 넘깁니다.
   - 브리프에는 목표, 배경과 이유, 요구사항, 아직 정하지 못한 점이 정리됩니다.
3. 지휘자가 계획을 세우고 실행자들에게 나눠 줍니다.
   - 여러 실행자가 동시에 움직일 수 있어서, 작업이 겹치지 않으면 병렬로 더 빨리 끝납니다.
4. 사용자만 할 수 있는 일(계정 권한 부여, 환경변수 설정, 앱 화면 조작 등)이 생기면 요청자가 "워크시트"(W-###, 버튼 위치까지 적힌 실행 안내서)를 만들고 소통자가 건넵니다. 체크리스트를 그대로 따라 한 뒤, 맨 끝의 회신 한 줄을 복사해 소통자에게 보냅니다.
   - 워크시트를 기다리는 동안에도, 막히지 않은 다른 작업은 계속 진행됩니다.
5. 이해가 안 되면 소통자에게 묻습니다. 소통자가 바로 답하거나, 요청자에게 워크시트를 고쳐 달라고 요청합니다.
6. 완성되면 검사자가 실제로 눌러 보고 결과를 보고합니다.
7. 진행 상황이 궁금하면 소통자에게 "지금 뭐 하고 있어?"라고 물어봅니다. 브리핑이나 그림으로 설명해 줍니다.

## 5. 사용자가 답해야 하는 순간

지휘자는 아래 다섯 가지 짧은 질문만 사용자에게 직접 던지고, 답은 지휘자 창에서 합니다. 판단에 설명이 필요하면 먼저 소통자에게 "이게 무슨 뜻이야?"라고 물어보고 답해도 됩니다.

1. "위험한 작업(삭제·배포·결제·보안)이라 확인이 필요합니다" → 예/아니오로 답합니다.
   - 되돌리기 어려운 작업이라 지휘자가 먼저 멈추고 확인을 구합니다.
2. "결정이 필요합니다" → 제시된 선택지 중 하나를 고릅니다.
   - 지휘자가 판단할 수 없는, 취향이나 우선순위에 관한 선택입니다.
3. "실행자 6명 넘게 필요합니다" 또는 "바꿀 범위가 넓습니다" → 비용을 승인할지 답합니다.
   - 큰 규모의 작업이라 미리 승인을 받습니다.
4. "Codex에 맡겨도 될까요? 남은 사용량이 충분한가요?" → 확인 후 답합니다.
   - Codex는 다른 회사의 코딩 도구입니다. 남은 사용량이 부족하면 작업이 중간에 끊길 수 있어 미리 확인합니다.
5. 요청자가 만든 워크시트를 실행하고, 끝나면 회신 문장을 소통자에게 보냅니다.

이 다섯 가지 외에 지휘자가 직접 쓰는 글은 한 줄짜리 상태 보고와, 같은 방법이 세 번 실패했을 때의 중단 보고뿐입니다. 그 외의 모든 설명과 질문은 소통자를 통해 오갑니다.

## 6. 하지 말아야 할 것

다음 네 가지를 지키면 에이전트들이 서로 충돌하지 않고 안전하게 일합니다.

- 비밀번호·API 키·카드번호를 채팅이나 워크시트에 적지 않습니다. 워크시트가 "본인 값"이라고 표시한 자리에 직접 입력합니다.
  - 채팅 기록이나 파일에 남으면 나중에 유출될 위험이 있기 때문입니다.
- 에이전트가 일하는 동안 `docs/` 안의 파일을 직접 고치지 않습니다. 바꾸고 싶은 내용이 있으면 소통자에게 말합니다.
  - 여러 에이전트가 같은 파일을 동시에 쓰고 있으면 서로 덮어쓸 수 있습니다.
- 실행자 창에 새 요청을 넣지 않습니다. 요청은 언제나 소통자에게 합니다.
  - 실행자는 받은 티켓 하나만 보도록 되어 있어서, 다른 요청이 섞이면 범위를 벗어난 일을 하게 됩니다.
- 창을 너무 많이 열지 않습니다. 기본 3개(지휘자·소통자·요청자)에 실행자 3~5개 정도가 적당합니다.
  - 창을 열 때마다 별도로 사용량이 발생합니다.

## 7. 어디를 보면 되나

- `docs/00_INDEX.md` 맨 위의 "현재 상태" 한 줄 — 지금 무슨 단계인지 요약입니다.
- `docs/tasks/BACKLOG.md` — 무엇이 진행 중이고 무엇이 끝났는지 보여주는 현황판입니다.
- `docs/briefs/` — 브리프·설명·워크시트가 쌓이는 곳입니다.
- `docs/tasks/T-###.md`의 "보고"와 "검증 기록" 칸 — 특정 작업 하나의 결과를 자세히 보고 싶을 때 확인합니다.

이 네 곳만 봐도 전체 그림을 파악할 수 있습니다. 그 밖의 문서는 지금 당장 필요하지 않으면 열어보지 않아도 됩니다.

## 8. 비용 감각

모델마다 사용료(입력 기준 단가)가 다릅니다. 비율로 보면 Fable 10 : Opus 5 : Sonnet 2 : Haiku 1입니다. 지휘자만 가장 비싼 Fable을 쓰고 나머지 역할은 더 싼 모델을 쓰므로 전체 비용이 줄어듭니다. 다만 세션(창)을 열수록, 또 실행자를 많이 띄울수록 사용량은 그만큼 늘어납니다.

그래서 지휘자 세션은 하나만 유지하고, 실행자는 작업이 끝나면 창을 닫는 식으로 사용량을 관리하는 것이 좋습니다.

effort 단계(생각하는 깊이)에 대한 자세한 설명은 9번 용어 사전을 참고하세요.

## 9. 용어 사전

| 용어 | 뜻 |
|---|---|
| 지휘자 | 계획을 세우고 결과를 검증하는 메인 세션. Claude Fable 5.1을 씁니다. |

## 10. 자주 묻는 질문

**세션이 뭔가요?**
Claude Code에서 여는 채팅창 하나를 말합니다. 창마다 맡은 역할이 다릅니다. 지휘자 창과 소통자 창은 서로 다른 세션이고, 서로 다른 대화 기록을 가집니다.

**창을 몇 개 열어야 하나요?**
기본은 지휘자·소통자·요청자 3개입니다. 화면이나 기기가 있는 제품이면 검사자를 더 엽니다. 실행자는 작업이 있을 때만 3~5개 정도 엽니다.

한 번에 열려 있는 창이 너무 많으면 6번 "하지 말아야 할 것"의 원칙에 어긋납니다.

**다음 날 이어서 하려면?**
지휘자 창을 다시 열면 `docs/00_INDEX.md`를 읽고 이어서 진행합니다. 진행 중이던 작업이 궁금하면 `docs/tasks/BACKLOG.md`도 함께 확인합니다.

**실수로 창을 닫았어요.**
같은 제목으로 세션을 다시 열거나 이어보기 기능을 씁니다. 기록은 `docs/`에 남아 있으므로 잃어버리지 않습니다. 어느 창이었는지 헷갈리면 제목(지휘자·소통자·요청자·검사자, 또는 티켓 번호)으로 구분합니다.

**Codex도 쓸 수 있나요?**
가능합니다. 다만 지휘자가 위임 전에 남은 사용량이 충분한지 먼저 물어봅니다.

확인 없이 맡기면 작업이 중간에 끊겨도 어디까지 반영됐는지 알기 어렵기 때문입니다.
